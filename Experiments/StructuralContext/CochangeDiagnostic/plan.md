# 変更された既存窓口の診断（#105）

**同じ構文変更が既存の複数領域へ入る場合は、その処理全体と既存利用側を案内できるかを診断し、共通化の必要性とは区別する。**

2026-10-05。#102 / PR #104完了後の既読診断。原input/レビュー位置と反対理由を`needs.json`へ固定してから実装する。通常CLI/libraryの検索契約は変更せず、自分のpackageの一時コピーへ診断entryを組み込む。第三者sourceとrawはignored。対象build/LLM/意味解決なし。

## 観測単位と比較する別案

1. 現行の関数索引＋宣言全体不変では、initializerや変更されたhelperが落ちる理由を別々に確認する。
2. 単に関数索引へinitializerを足す案では、変更された既存窓口を除外する条件は残る。
3. 最小の別単位として、switch領域の前後の構文形を比較する。字句宣言headerと条件、switch式の記載が前後各一意の場合のみ対応。各caseのラベル表記・callの記載形/明示ラベル列/trailing closureを同じ順序で持つ二つ以上の領域に、同じ形の変更が入った関係を示す。引数値を同一視せず別途差異として残す。本文全体一致・挙動同一・解決済みcalleeとは呼ばない。
4. 関連領域の所属宣言、条件、本文変更と、同じselectorが書かれた別の実行領域を前後位置付きで示す。initializer・property/accessor・closure等の範囲を明記。名前一致は利用先の証明ではない。対応が重複する領域は不明として残し、順番で対応させない。

2case以上は危険度や最適な統合先の閾値ではなく、今回の診断対象の構文範囲。引数やcase名の改名を正規化しない。条件の有効性、receiver型、呼出先、値、性能、意図を推論しない。似た構文で目的の異なる対照は同じ事実を返し得るため、不明表示と通常読解を必要とする。

## 終了と撤去条件

固定必要位置へ届いても、既読例の診断成功に留める。全3成立inputを再生し、全process bytesの二回一致・入力SHA/全一覧・全位置を照合する。正常0とread/parse失敗を分離し、部分出力を拒否する。曖昧対応・追加削除・条件違い・共有済みhelper・異なる目的/引数の対照を置く。独立code/結果点検、自己利用、Actions/実Bot/成果物までが1PR。

関係が事実として再現でき、差分外の必要な処理/利用側へ届けば、最小の実験CLI契約を別PRに分解する。意味推測や既読固有ruleが不可欠、または範囲だけ増えて必要関係を案内できなければ方式を撤去/再設計する。次の未読比較は両stage1へ同じ通常diffを渡す契約を事前固定する。独立比較でも配置再検討への寄与が得られず、決定論的に取り出せる別根拠がなくなった場合は、目的未達のままルール追加を続けず、用途限定またはプロジェクト撤退を人間へ判断事項として知らせる。本番/M3は保留。
