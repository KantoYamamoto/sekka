# [M2/検証単位] 固定した差分外案内を別の実PRで独立比較する

親: #71。前提: #85 / PR #86の事実性確認とmerge。評価器はPR #86最終headの実験package、現在の保存binary SHA-256 `5376f29bdbfb15a24c150792c43b77da33d53704b65050c0a0adbbd2c2bb7626`（Swift 6.4 / SwiftSyntax604.0.0）。評価中は実装/候補条件を変更しない。

## こういう場合はこうする
既知例に到達できたら、出力で選び直さない別のPRで通常diff/検索と独立比較する。0候補・解析失敗・反対理由も結果に含め、必要性の薄い案内を成功としない。

## 目的と選択理由
新しいmember表記経路はreceiver/実callee未解決の弱い関係であり、既知helperへの到達だけでは探索負担や誤誘導を判断できない。配置を見直す問いと現配置を支持する理由へつながるか、diffのみでは探しづらい実装を読む入口になるかを調べる。候補を増やす実装を先に足さない。

## 入力の固定（出力閲覧前）
#77と同じ2repo（apple/swift-collectionsのSources/、groue/GRDB.swiftのGRDB/）、merged<=2026-09-21、作成日降順・同時刻は番号降順、GitHub search API `repo:... is:pr is:merged merged:<=2026-09-21`の先頭40件（UTCの日付包含境界、paginationで範囲を増やさない）。#77で読んだCollections728/727、GRDB1876/1869を除き、production prefix内Swift変更を含む最初の2PRずつ。コメントだけの変更も含める。候補メタデータ一覧・順序・除外理由を保存する。選択者は適格性のmetadata/変更pathだけを読み、bodyの取得は未閲覧の資料保存に限る。他の既読PRも判明したら理由付きで除外し、事後に未見扱いしない。これは別PRの未読レビューでありrepo自体の未見とは呼ばない。足りなければ不足として扱い、repo/日付/条件を変えて穴埋めしない。選択前にsource/body/機械出力は読まない。

各PRのmerge-baseとheadを固定。production prefixのSwift全件、変更ファイル、license、PR本文をGET取得。Git tree/blobとSHA-256/サイズ・ファイル一覧、diffを照合。非Swift変更/テストも両担当に同じ資料を渡す。archiveの安全なregular fileだけ読み、targetのcheckout/build/scripts/testを実行しない。manifestと評価器hashを実行前にcheckpointする。実験source commit/lockfile、OS/Swift、CLI引数、packet hash、diff取得API/context/rename条件を保存。評価器sourceが変わったら入力/出力閲覧前に凍結し直す。二回一致はexit code/stdout/stderrの全バイトを比較し、非決定字段の除外はしない。

## 独立比較の手順
- caseごとに履歴を継承しない新しいA/Bを作成（レビュー時のみsub-agent）。共通課題文・allowed path・検索方法（rg/通常のfile読取り）を固定。開発側の所見、本計画レビュー、相手のcheckpoint/結果、他caseの所見を渡さない。共有workspaceでもallowed path以外を読まない指示を明示。誤閲覧/既読は独立扱いせず逸脱記録とする。
- stage1: 両者同じPR本文を読んでから、Aには通常diffだけ、Bには凍結評価器JSON/textと利用範囲だけを渡す。別のstage1ディレクトリへ必要資料だけを配置し、hashを保存。Bへ普通のdiff/共通sourceをまだ渡さない。両者が初期確認先・暫定の問い/不明のcheckpointを保存して完了したことを確認する。0候補もそのまま保存する。
- stage2: checkpoint確認後に同じ通常diffと検索可能なbefore/after sourceを両者へ開放。A/Bの結果保存先は別にし、相互閲覧しない。資料と開放のcheckpoint hashを記録する。
- 両者は実装目的、必須の未変更箇所と位置、変更との関係、同じ局所修正を継ぎ足す具体的負担、別配置と妥当になる条件、現配置を支持する理由、不明範囲を記録。根拠がなければ配置変更を提案しない。読んだ場所/追加検索/見送った候補を短く記録し、初期候補→検索後の追加発見→最終判断を対応付ける。
- Bはcandidateごとに関連性・必要性・通常diffのhunk/context露出・配置検討への実際の使用を別欄へ記録。候補/入口の省略と未到達の必要確認先を調べる。関連と必須確認を同じ扱いにせず、SDK/範囲外・callee未解決を無視しない。
- 最後に両結果を照合する。結論の一致は独自発見の証拠にしないが、読む先の案内と最終根拠への寄与は別に記録。担当差も含む比較であり、時間/token費用や人間の負担削減を結論しない。実行時間/出力量は補助指標。A/Bの必要箇所の合併を網羅的な正解集合にせずprecision/recallを主張しない。統合担当が両結果を読むこと、固定機械出力とAI所見の再現性が異なることを開示する。

## 判定と次の一手
各caseで、候補の事実性→必要確認先への到達→探索の寄与→配置の問い/反対理由を分ける。構造目的の支持には (1)変更と既存実装の位置/関係 (2)局所追加の反復で発生する具体的負担 (3)その負担に対応する別配置と成立条件 (4)現配置の支持理由/不明、全ての根拠が必要。Bの初期案内がどの根拠に使われたかを対応づける。挙動確認先や一般的な質問への到達は案内の結果であり構造目的の合格ではない。両担当に根拠がなければ配置目的は判定不能/未支持と記録。探索寄与だけなら用途限定の候補とし、構造目的を達成した理由でM3へ進めない。根拠なく「統合が必要」と誘導したら失敗。候補が出たこと/正しいと断定しなかったことだけで合格しない。全て0・必要な差分外確認先なしなら標本で判定不能とする。解析失敗は正常0に数えない。

この小標本は全Swift PRや人間レビューの有用性の証明ではない。結果によって継続/用途限定/方式変更/保留を#12/#71へ反映する。利益が弱ければM3へ進めない。
