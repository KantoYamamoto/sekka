# 変更を全体へ組み込むための開発手順

**要求を追加・変更する場合は、コードや文書の配置と、プロジェクト全体の目的・優先順位を一緒に見直す。**

## 着手時に確かめること

Issueには「どの利用場面の、どの検討を助けるためか」を書き、既存の役割へ組み込む案、置き換える案、今回は見送る案を比較する。小さな修正は数文でよい。全件に大きな設計書は要求しない。

局所では、責務の重複、入口の増加、依存・状態の配置、同じ説明の分散を確認する。プロジェクト全体では、目的との関係、マイルストーンの終了条件、既存Issueの必要性を確認する。「実装できる」「未対応だった」だけを着手理由にしない。

ユーザーの追加要件で前提が変わったら、既存計画を書き換える。新しいIssueだけを末尾へ追加しない。不要になった課題は理由付きで閉じ、保留する課題は再開条件を明記する。根本的な目的変更や大きなスコープ拡張は根拠と選択肢をユーザーへ示す。

## 実装・文書を変更するとき

1. 関係する既存実装・文書を読み、変更後の配置を決める。新しいファイルや節は明確な読み手・役割が必要な場合に作る。
2. 要件を既存の説明と統合し、重複・古い説明・矛盾を取り除く。現行仕様を履歴の追記で表現しない。
3. 判断と理由は[判断記録](decisions/README.md)へ、実測は検証記録へ残す。READMEは利用の入口、ROADMAPは現在の計画とする。
4. 適切なテストを実行し、通常diffに加えて変更後のファイル全体と隣接する責務を読む。

## PRで残す根拠

PR本文には、利用者の問題と変更後の挙動、既存構成への組み込み方、取り除いた重複や維持した境界、検証結果を必要な長さで書く。プロジェクトの方向や優先順位を変えた場合は、その理由と旧タスクの扱いも書く。

自己レビューでは、実装が正しいかだけでなく「この変更を入れた全体を、最初からこう設計するか」を問う。答えが否なら、必要な再配置や段階的移行を同じスコープで行うか、残す負債と理由を明示する。全面書き換えを毎回求めるものではない。

## Sekkaを自己利用する

Swiftの実装変更では[比較手順](validation/protocol.md)に従い、新旧評価器の出力と通常diffを読む。対象コードをSekkaに見せるためだけに型へ包んだり分割したりしない。

Sekkaが案内できた場所と、通常diff・周辺文脈で初めて分かったことを分けて記録する。READMEの読み順や開発計画の目的との一致は、現行のSekkaには評価できない。そこを人間・AIが点検する責任は残る。観測件数の増加を、全体の整合性の向上と同一視しない。

固定の境界確認は`python3 Scripts/review_probes.py`で実行する。15ケースの結果は`.build/review-probes.json`に保存される。期待終了コードが合うことと、レビューの有用性は別である。
