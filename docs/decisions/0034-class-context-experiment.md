# 0034: 追加型と既存の実装配置を結ぶ実験

**方針：新しい型を受け入れる場合は、変更一覧だけでなく既存の親・兄弟の同じメソッド表記を並べる材料を試し、実装不足や共通化の必要性とは判定しない。**

- 記録日：2026-09-09
- 状態：実験として採用。本番未採用
- 経緯：#56で反復抽出では届かない配置の問いを確認し、#57で必要な関係を選び直す。

## What / Why

入力内に新しく現れたトップレベルclassについて、単純な継承名に一致する既存classと、その表記を共有する既存classを関連候補として並べる。親候補の空本体と、既存兄弟候補のoverrideが同じメソッド表記にある場合、その位置と追加型側の一致宣言を出す。空本体は文のないbodyに限定し、return nilやfatalErrorを意味上の空実装へ変換しない。

新しい子への追加だけを読むと、既存兄弟に残った共通処理を見落とす。この組合せは#56のソースレビューで配置の問いに結びついた。全型を一覧するより材料を限定できる見込みだが、読み手の利益は未確立。

## Why not

呼び出し反復の条件を緩める案は採らない。今回の根拠は反復そのものではなく、空の共通入口と兄弟の実装位置だった。型名を解決した継承グラフとして扱う案も採らず、同じ表記から得た候補と呼ぶ。空hookは意図的な場合があり警告や終了コード1にしない。

## How / 限界

SwiftSyntaxでトップレベルclassと単純名のextensionを収集し、メソッド名・引数ラベル/型・効果指定・戻り型・generic表記を照合する。内部引数名とoverride/access修飾子は照合キーから除くが、静的なメソッドは対象外。同名型の複数宣言、メンバー宣言の条件分岐や限定付きextensionがある型は候補の照合から外し、前後を区別して理由を残す。関数本体内の#ifは宣言の存在を変えないため除外条件にしない。

型解決・動的dispatch・外部extensionは不明。追加型側の空配列は「入力内の一致宣言なし」であり実装不足の証明ではない。名前・引数ラベルは同じでも型等の表記が違う宣言を別欄に残す。実入力のEditorStateとGutenbergKit.EditorStateを同一視せず、存在する宣言を見えなくしないため。本体のない宣言はunavailableとし、空の本体とは区別する。

入力収集の境界は0032で検証したものを引き継ぎ、構文エラーで部分結果を出さない。実験結果は[記録](../validation/class-context-experiment.md)へ残す。従来の反復実験は履歴で再現可能にし、新旧の実験基盤を常設しない。

2026-09-12、材料レビューを受けて出力単位を前後の配置へ修正した。各メソッド表記について親・兄弟・追加型それぞれのbefore/after宣言集合を出し、同じ表記と別表記を分ける。既存の親にあった処理を今回子へ移した場合も、空の親が昔からあった場合と区別して読めるようにする。メソッドを一対一で対応付けたり、コードの移動を検出したと断定したりはしない。変更後だけの位置対照を残して注意書きを足す案は、実際の変更方向の取り違えを防げないため採らない。

## 見直す条件

WordPressは既知の開発入力なので一致だけでは成功としない。意図的な空hook・追加型にも実装がある例・同名型・extension・条件付き宣言を対照にし、関係の捏造と過剰な統合誘導を確認する。未読の実変更で必要な材料を得られなければ、この方式も置き換える。継承のないLogger例を解決したことにはしない。
