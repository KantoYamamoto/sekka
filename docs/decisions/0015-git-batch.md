# 0015: Git blobをバッチ取得する

**方針：固定Gitスナップショットを読む場合は、必要なblobをまとめて取得し、バイト長で検証する。**

- 記録日：2026-09-06
- 状態：採用
- 経緯：Issue #13。M1の自己利用で約30ファイルの比較が8〜9秒かかった。

## 目的・状況

source diffの再表示でも解析を行うため、待ち時間がレビューの負担になる。従来は1ファイルごとにGitプロセスを起動していた。

## What — 選ぶこと

対象Swiftファイルをls-treeで選別した後、一意なblob IDをcat-file --batchへまとめて渡す。同一blobを使う複数パスは1取得の結果を共有し、型のパス別識別は維持する。

## Why — 選ぶ理由

解析の意味や入力を変えずにプロセス起動回数を減らせる。永続キャッシュを作らないので、古い内容を誤って再利用する条件を増やさない。

## Why not — 別案を採らない理由

ファイルごとの並列起動は起動回数自体を減らさない。checkoutは対象作業ツリーへの干渉になる。永続キャッシュ・常駐プロセス・差分ファイルだけの解析は今回の原因より範囲が広い。

## How — 実現方法

[Inputs](../../Sources/SekkaCore/Inputs.swift)で入力ID一覧を一時ファイルからstdinに渡し、stdoutを読みながらGitの完了を待つ。双方向pipeの詰まりを避ける。[GitBatch](../../Sources/SekkaCore/GitBatch.swift)で期待ID、blob型、バイト長、終端改行、UTF-8、余剰データを検証し、不正なら部分結果を返さない。

## 制約・見直す条件

バッチ全体をメモリに保持する。巨大リポジトリでメモリが問題になれば逐次decodeを検討する。性能は同じ入力・環境で新旧を交互に複数回測り、キャッシュや並行作業の影響を明記する。

## 根拠・確認

Unicode、ヘッダーに似た本文、末尾改行なし、空blob、途中切れ、不正長、非UTF-8のテストと、同一blob複数パスのCLIチェックを行う。固定入力での内容一致・実行時間・自己利用の結果を検証記録へ残す。
