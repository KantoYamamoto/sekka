# 追加型と既存の実装配置を結ぶ実験

2026-09-09開始、2026-09-12更新。[#57](https://github.com/KantoYamamoto/sekka/issues/57)、判断[0034](../decisions/0034-class-context-experiment.md)。本番未採用。#56の実例で、呼び出し反復ではなく空の共通入口と既存兄弟の実装が配置の問いの根拠になったため、実験を置き換える。

## 変えたもの

新しいclass名から、入力内に前後とも一意なclass宣言のある親候補と既存兄弟候補を探す。親の空bodyと兄弟のoverrideに同じメソッド表記がある場合、追加型側の宣言も並べる。型解決・実装不足・必要な共通化は断定しない。

新しい処理がないという判定にしないため、bodyなしの宣言もunavailableとして残し、名前と引数ラベルが同じでも型等の表記が違う場合は別欄へ出す。同名・条件付きメンバー・限定付きextension等で候補を絞れない場合は、前後を区別して省略理由を残す。

各slotは親・兄弟・追加型それぞれのbefore/after宣言集合を持つ。変更後だけでなく、親にあった処理を今回子へ分けた場合の状態と位置も示す。集合は同じ名前/selectorの候補であり、一対一のメソッド対応やコード移動の検出とはしない。

旧CallSequencesのSwift packageと常設CIは撤去した。既存のディレクトリ入力の境界だけを引き継ぎ、JSONは関係の組へ変更した。旧実験は[固定commitでの再現](../../Experiments/CallSequences/README.md)と検証記録を残す。小さな試作を第2・第3の製品として並行保守しない。本番SekkaのCLI/schemaは変更していない。

## 試験と修正

- Swift 18テスト：未変更親/兄弟の位置、追加型にも実装がある対照、意図的な空hook、今回の分離、前後の別表記とoverload、複数ファイルのextension、同名・generic・qualified名・型/ラベル/効果の差、構文エラー、JSON順序。
- CLI：前後ファイル数、同一入力と繰り返し実行の安定性、dot名の祖先/ルート・Finder非表示属性、部分出力のない構文エラーとsymlink拒否。
- 固定OSS入力：manifestの全Swiftパス/SHA-256と収集件数を照合し、代表メソッドの行位置と別表記の宣言を確認。対象コードは実行しない。
- 本番：Swift 65・CLI/Git 39・Python 13チェック成功。本番のコードは変わらないため、実験の後続修正では実験側の試験を再実行した。

初回は関数本体内の#ifまで型の候補除外に使い、WordPressの親を落として0組になった。これは宣言の存在条件と本体の条件を混同したため。メンバー宣言を分岐する#ifだけを候補除外へ使い、両者の対照テストを追加した。

独立実装レビューでは、bodyなし宣言を捨てると「入力内に一致宣言なし」が事実と違うことを確認・修正。再レビューで解消を確認した。前後の候補除外理由と説明のずれも修正した。

## 固定実入力の結果

| 入力 | 関係の組 | メソッドの組 | 解釈 |

| WordPress #25208、15→16 Swiftファイル | 1 | 8 | 新しいCustomPostEditor、親PostGBKEditor、既存NewGutenbergEditorを結ぶ。媒体要求の親145行・兄弟262行は#56の問いの位置と一致 |

履歴イベントでは親のGutenbergKit.EditorStateと追加型のEditorStateの表記が違う。名前/ラベルが一致する別表記として追加型67行を添える。意味的に同じ型とは解決しない。8組には媒体選択以外のイベントも含み、全件が設計上の問題という意味ではない。

媒体要求は親before:136/after:145がともにemptyで、既存兄弟before:212/after:262には文がある。履歴更新は親before:119のstatementsからafter:127のemptyへ変わり、既存兄弟にafter:227の実装が現れる。この対照を実入力検証で固定し、「前からある非対称な配置」と「今回の分離」を読み分けられることを確認した。

未変更helperのAbstractPost→Blogという依存縮小の根拠は、この試作には含まれない。親・兄弟の配置の入口を出せても、具体的な移動方法の検討にはソースを読む必要がある。WordPressは実装の選定に使った既知入力で、検出できたことを未読入力での有用性へ一般化しない。

## 独立した材料レビュー・自己利用

独立担当は変更後だけの初期出力から、媒体・履歴・modalの具体的な問いへ進んだ。ソースで確かめると、履歴は異なるUI所有者への操作、ロードや内容更新は既存側の計測/autosave依存であり、全部を共通化する提案は不適切だった。未変更helperのBlog依存はソースを読んで初めて分かった。

さらに、履歴/modal処理はこのPRで親から子へ移していた。初期出力だけでは逆向きの再統合を促し得るため、before/after集合へ作り直した。同じ既知入力の修正レビューで変更方向が読み違えにくくなったことを確認。これは未読PRでの有用性の証明ではない。

Firefoxでは抑制guardと独立した広告取得Taskの寿命を揃えるべきかという配置の問いがソースから得られた。新しいclassのない本試作はそこへ案内できない。0件を、局所追加が妥当という判定や有用性の成果に数えない。

初期実装`2c6134d`と最終実装`c4a08fc`を開始前`c8ddc0b`から自己利用し、どちらも新旧評価器のfull JSONは同一。Sekkaは新旧の型の置換を案内するが、collectorの事実性、CLI境界、CI順序は通常diff/実装レビューで確認した。最終出力の21パス・Swift8・21観測・23本体未比較は理解の補助であり、独立レビューの代替ではない（Gitのrename有効一覧は19パス）。最終のrawは`.build/self-review/class-context-final`。AGENTSの文書変更を取り込んだmergeではSwiftを変更していない。

## 次の判断

本番への採用は保留する。この材料が具体的な問いへ進むことは確認したが、継承と空hookという狭い形に限られる。次は選定に使っていない変更と意図的な拡張点を対照に、不要な改修への誘導と取りこぼしを確かめる。必要な関係がこの形に収まらなければ枠組みを見直す。成功条件0031を維持し、継承のないLoggerやプロジェクト全体の整合まで扱えたとは主張しない。
