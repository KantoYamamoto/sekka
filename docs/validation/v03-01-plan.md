# V03-01: 最初の独立比較の実施計画

**有用性を比較する場合は、実装経緯を知らない担当に同じ入力・課題を渡し、結果を見る前に評価条件を固定する。**

Issue #8。準備済み・レビュー未実施。前提となる小さな表示変更はPR #33。2026-09-07にユーザーが、この比較について独立したAI 2件の実施を許可した。その他の作業への包括的な委任許可とは扱わない。

## 対象を選んだ理由

公開OSS Nukeの[PR #953](https://github.com/kean/Nuke/pull/953)「Return ImageTask.Progress from FetchImage and LazyImageState」。進捗を表す既存型とUI側APIの変更を扱い、既存の構造との関係を確認する課題に合うと、タイトル・ファイル一覧から判断した。

選定担当はPR本文・レビューコメント・Swiftの差分内容をまだ読んでいない。既に試した私有アプリのPRを未読の代わりに使わない。ここでの1件は比較手順の試行でもあり、一般的な有効性の証明ではない。

- base: `e90e9f2daf1a089b4c88eb07fe50f38460bd08cb`
- head: `d66af7a929c09f69d260c3a8a5ece26fabc6bed6`
- merge-baseは上のbaseと一致することをGitで確認。
- 変更: Swift 4ファイルと文書2ファイル（メタデータのみ確認）。

## 両担当への共通課題

この変更を受け入れる前に、既存のAPI・状態更新・利用側とどう整合するかを確認するための場所を、理由付きで最大5件選ぶ。各項目にファイル・行、観測事実、検討したいこと、不明な文脈を分ける。見つからない不具合を作らず、型名だけで役割や依存先を断定しない。

関係する周辺コードや同じsnapshotの文書を追加で読める。追加検索・diff展開と目的を記録する。対象アプリ/ライブラリのビルド・テストは行わず、外部のPR議論・既存レビューは読まない。

## 条件

- A: 通常のSwift diffと固定snapshotへのアクセス。Sekka出力は提供しない。
- B: Aと同じ入力に、固定したSekkaバイナリのtext/compact/full JSONを追加。必要に応じ通常diffへ進む。
- 同じモデル・推論設定の別セッション、または同等条件を説明できる担当を使う。担当同士の出力・この検証の途中結果は共有しない。
- Mermaid試作は両方に渡さない。図の効果を同時に混ぜない。

この比較はSekka併用全体と通常diffのみの違いを調べるもので、#31の文脈追加だけの効果を分離する実験ではない。文脈追加単独の判断が必要なら、後で旧版と新版の別比較を設ける。

初読開始と終了時刻、ツール実行を含む時間、追加検索・展開の回数を記録する。待機・通信等を分離できなければ時間は参考値に留める。token数は取得できる場合のみ記録し、文字数で代用しない。異なるモデル・人間とAIなど条件差がある場合は同条件の速度比較を主張しない。

## 結果を受け取った後

1. 選定担当が通常diffと周辺コードを読み、各確認先の根拠が実在するかを照合する。全バグの正解集合を作ったとはしない。
2. 既存の役割/APIを照らす具体的な確認先、追加で必要だった文脈、根拠のない統合・分割の誘導、読む負担を比較する。
3. Bだけに有用な確認先や検索削減があったか、Aでも同じことが容易に分かったか、追加文脈がノイズになったかを記録する。
4. 継続・表示を戻す/任意化・判定不能のいずれかと、次の1検証を選ぶ。1件の結果でM2全体を完了しない。

## 再現と現在の停止点

入力repoとA/B別の資料はローカルのGit管理外に保存する。バイナリhash・入力ID・資料hashをmanifestに固定する。公開資料には評価手順と検証結果を残し、OSSのソース全文は複製してコミットしない。

準備時点では担当方法の確認待ちだったが、現在はユーザーが実施を許可済み。開発会話を渡さない独立した担当2件に、各条件の資料だけを渡す。新しい試用報告への改善はまだ入れず、現行版の基準点として実施する。
