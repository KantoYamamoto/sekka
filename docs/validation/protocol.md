## 自己利用の手順

1. Swift変更前に旧評価器を退避する。実装・テスト後に小さいローカルコミットを作る。
2. `python3 Scripts/self_review.py --base HEAD^ --head HEAD --baseline-binary .build/evaluation-baseline/sekka --output .build/self-review/run-01`でレビュー資料を作る。指定refは完全なコミットIDへ解決し、評価器もコピーしてSHA-256を記録する。出力先はGit管理外、既存フォルダは上書きしない。
3. `candidate.text`から確認先を選び、`ordinary.diff`とSwift以外の差分も読む。`review.md`に、役立った案内・不足・次の1改善・再現ケースを記録する。合否判定や自動修正は行わない。
4. 公開できる所見だけを`docs/validation/`に要約し、実装と別の記録コミットにする。新旧JSONのcoverage・理由・観測を比較して欠落を点検する。

自己利用の目的は問題を早く発見すること。実装者は差分を既に知っているため、自己評価をM2の独立した比較レビューの代わりにしない。Sekkaの都合に合わせてテストを型に移すなど、入力側を観測しやすく歪めない。

## M1の判定基準

- 型全体のN本体追加・削除の理由は型ごとに1説明。名前は宣言一覧から読める。比較省略の件数は維持。
- 既存型での改名・引数変更・重複IDは、確定的な新規追加と推測せず個別表示。
- 共通#if説明は標準textで1回。前後別の位置は詳細JSONに残し、新しい条件ブロックの候補は曖昧さと区別する。
- 指定した比較元・先のdiffを取り出せる。変更後の作業ツリーに古い行を流用しない。
- 文字数・行数とツール実行時間を記録する。レビュー時間・token費用と混同しない。

## M2の比較手順と不足

未試用のAPI/モデル、SwiftUI、本体・型の分割削除、小さいPRを各1件選び、事前に比較コミットと確認課題を固定する。現時点で未試用の対象4件は未確保。既知#81/#78や今回自分で実装した差分を代用しない。

A=通常diff、B=Sekka＋必要なdiff。独立レビュアー/セッションを優先し、同じ人が再読する場合は順序と慣れを記録する。初読から理由付き確認先一覧までの時間、準備込み総時間、追加検索・展開数、通常diffとの照合での確認項目漏れを記録する。基準項目は全バグの正解集合ではない。

異なる複数ファイルPRで繰り返し手間が減り、確認項目の欠落が増えない場合に継続を検討する。出力量だけ減って確認作業が変わらない場合や重要な場所が隠れる場合は、機能追加より用途・観測方針の見直しを優先する。条件差で判断不能なら追加1検証の理由を記録する。
