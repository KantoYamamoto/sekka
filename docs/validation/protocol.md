## 自己利用の手順

1. Swift変更前に旧評価器を退避する。実装・テスト後に小さいローカルコミットを作る。
2. `python3 Scripts/self_review.py --base HEAD^ --head HEAD --baseline-binary .build/evaluation-baseline/sekka --output .build/self-review/run-01`でレビュー資料を作る。指定refは完全なコミットIDへ解決し、評価器もコピーしてSHA-256を記録する。出力先はGit管理外、既存フォルダは上書きしない。
3. `candidate.text`から確認先を選び、`ordinary.diff`とSwift以外の差分、変更後の文書・モジュール全体も読む。`review.md`に、どの構造上の検討に役立ったか・不足文脈・次の改善か見送り・再現ケースを記録する。合否判定や自動修正は行わない。
4. 公開できる所見だけを`docs/validation/`に要約し、実装と別の記録コミットにする。新旧JSONのcoverage・理由・観測を比較して欠落を点検する。

自己利用の目的は問題を早く発見すること。実装者は差分を既に知っているため、自己評価をM2の独立した比較レビューの代わりにしない。Sekkaの都合に合わせてテストを型に移すなど、入力側を観測しやすく歪めない。

## M1の判定基準

- 型全体のN本体追加・削除の理由は型ごとに1説明。名前は宣言一覧から読める。比較省略の件数は維持。
- 既存型での改名・引数変更・重複IDは、確定的な新規追加と推測せず個別表示。
- 共通#if説明は標準textで1回。前後別の位置は詳細JSONに残し、新しい条件ブロックの候補は曖昧さと区別する。
- 指定した比較元・先のdiffを取り出せる。変更後の作業ツリーに古い行を流用しない。
- 文字数・行数とツール実行時間を記録する。レビュー時間・token費用と混同しない。

## M2: 構造を見直す気づきの比較

成功条件は[0031](../decisions/0031-structural-success.md)。理由付きの「変更箇所一覧」では足りず、**変更 → 既存構造との関係 → 局所修正を繰り返す負担 → 再検討する配置と反対理由**まで根拠がつながるかを調べる。意味上の正しさや設計の唯一解は自動判定しない。

### 材料・抽出・実用性を分ける

1. 既知の合成対照で、どの構文事実・位置があれば問いに届くかを確認する。手作業カードは材料の仮説であり検出機能ではない（#52）。
2. 必要な事実を機械抽出する場合は、名前・型解決の曖昧さ、反復の配置数と前後差、対象外を検証する。期待したカードが1件出ることだけを合格にしない。
3. 未読の実変更で、普通のdiff/検索と比べて既存構造へ立ち返れた根拠と、不要な改修への誘導を記録する。最終的な有用性はここで検証する。

A=通常diff、B=Sekka/検証する材料＋必要なdiff。Bは通常diff・周辺コードを読む前に理由付き候補のcheckpointを保存する。固定資料を事前取得しSHA・packet hashを照合する。独立担当を優先し、既読・手作業・合成の条件は記録する。方針違いだけの同一コードには同じ観測を返し、両担当に同じ外部文脈を渡す。

結果には具体的な位置・関係・問い・別配置が妥当となる条件・不明範囲・発見の出所を残す。「統合/分割が必要」と根拠なく断定した対照は失敗として扱う。候補数、出力量、検索回数、時間は補助指標とし、中断・通信を分離できない時間は速度比較に使わない。通常diff側も同じ問いへ到達した場合は固有の利益を確認できたとはしない。
