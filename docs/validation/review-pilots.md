# M2予備試行: 案内から選んだ確認先の照合

2026-09-07。Issue #19。実行前に以下の条件を固定した。

## 条件

- 評価器: Sekka main `390dfba`からビルド。
- 私有アプリの未試用PRを2件。API/model: `c391f7d94b4cae344355fe1099abc2249018cd1e` → `770f338c10b174b1e383a29e1a78b9c02dd11269`。小さいSwift: `18ac7b2f9cbaa71aefcdb29ff1bde27805a3380c` → `0226c694e7f4c4c1ff5e291aaf22fbb578df2ed3`。いずれもbaseが共通祖先であることを確認。
- 同じAIがSekkaを先に読み、確認先を保存してから通常diffを読む。事前にPRタイトルと変更ファイル一覧を読んでいる。アプリの既知PRについての会話もある。
- 課題: 追加・変更された契約、既存経路への接続、通常diffで追加確認すべき場所を列挙する。
- 生出力・ソースはGit管理外。公開するのは集計と所見。
- 出力量とツール実行時間は測る。独立A/Bでないためレビュー時間短縮を主張せず、M2各ケースの完了に代用しない。対象アプリはビルド・テストしない。

## 結果

### Sekka初読 → 通常diffの照合

API/modelケースでは、モデル追加引数と取り込み処理、新判定器、新しい形式選択処理、画面の表示/入力/送信、追加テストの5群を確認先として先に保存した。通常diffでそれらの接続を読めた。一方、既存経路へ渡す条件、正規化オプション、数式・閾値の値は通常diffで初めて具体化した。構造案内から正しい接続や値を保証できない。

小さいSwiftケースでは、既存のデータ整合性テスト1関数が案内された。通常diffの追加12行を読むと、2言語それぞれで提示可能性と本文を検査する変更だと直接分かった。Sekkaはその保証内容を説明せず、初期text 1,310文字に対してSwift diffは1,325文字だった。先に案内を読む利益はこの試行では見いだせなかった。PR全体の大部分を占めるJSONデータは解析対象外で、Swift diffの大小だけでも適用価値を判断できない。

これは選んだ箇所の照合であり、アプリの完全な回帰レビューではない。独立A/Bの時間・検索回数・見落とし差は未測定。通常diffを本体ごとに再検索して読む操作が加わったことは記録するが、後から厳密な操作数を推定しない。

### 見つけた反復と今回の改善

API/modelの初期textは39,559文字、Swift diffは45,460文字、compact JSONは72,097文字。textのうちparameter-typeの行だけで26,778文字あり、長いinitializer宣言が各行に再掲されていた。観測19件という件数では、この負担を説明できない。

[判断0017](../decisions/0017-reference-presentation.md)に従い、同じ宣言の参照サイトを前後別にまとめる。参照を件数へ置き換えず、役割・型表記・宣言全文を残す。Swiftテスト43件・CLI/Gitチェック27件を確認。固定入力での短縮量とJSON保持、自己利用・Actions結果を追記する。

### 次の判断

新ルール追加やscan強化より、まずこの反復を取り除く。小さいSwift差分を自動で解析対象外にする閾値は採らない（サンプル1件であり、短い差分でも重要な契約変更はある）。M2本比較には新しい対象と独立条件が依然必要で、今回見た2ケースを未見の比較として再利用しない。
