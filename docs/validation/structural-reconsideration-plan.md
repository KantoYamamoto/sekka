# 構造の再検討へつながる材料の検証

2026-09-09、Issue #52。判断[0031](../decisions/0031-structural-success.md)。条件を結果受領前に固定する。

## 既存検証との違い

#29のLogger二条件はコードが同一で、違うのはチーム方針だけだった。同じ観測を返すのは正しい。そこで統合・分離を言い当てることを目標にしない。SwiftUIの分岐増加やモデルのメソッド増加も、根本的な見直しが必要という証明ではなかった。

今回は[7例](../../Fixtures/structural-reconsideration/cases.json)を固定し、変更を呼び出し側に配る場合と窓口内に留める場合の違いを調べる。合成・既知入力で、作者は狙いを知っている。独立レビューをしても実PRのM2完了にはしない。

## 事実カード案

手作業で確認した呼び出し表記・並び・配置数・前後位置と、既存窓口の短い該当箇所を並べる。呼び出し先を解決した依存グラフとは呼ばない。「統合すべき」「責務重複」といった答えはカードへ書かない。位置・表記は実ソースと照合する。

反復のない対照には無理にカードを作らない。同一コードの方針違いには同じカードを使う。方針は出力とは別に、両レビュー条件へ同じ資料として渡す。現行text/JSONの出力も保存し、何が欠けていたかを照合する。

## 独立レビュー

Aは通常diffと全ソース、Bはカードを先読みしてcheckpointを保存した後に同じ通常diff/全ソースを読む。レビュー課題は「受入前に確認する保守上の論点を最大2件。位置と理由、配置を見直す案、別配置が妥当となる条件。問題がなければそう記録」。各条件は新しい会話履歴なしの担当へ渡し、他条件・期待結果を見せない。名前は中立のケースIDに置き換える。

結果は0031の各条件に対して原文の根拠を示して採点する。候補数・時間の競争にしない。誤って統合を断定した対照、追加情報で初めて根拠を得た項目、カードなしでも到達した問いを記録する。先読みの答えだけで成功とせず、diff後も成立するか確認する。

## 次の作業を選ぶ条件

カードに具体的な根拠があり対照を誤誘導しなければ、その事実をSwiftSyntaxで取り出せる範囲を1実装単位として検討する。手作業カードの有用性と自動抽出の再現性は別ゲート。利益が弱ければカードを製品へ増設しない。ユーザーの設計方針を仮定しないと進めない場合、具体例とともに判断を求める。
