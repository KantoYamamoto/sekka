# 目的と次に試すこと

## 合意した方針

- Swift 6以降を対象にする。
- 人間・AIが「ここは設計を見直す材料になりそう」と気づける、linter寄りの道具。
- 毎回LLMでコード全体を再評価することを避ける。ローカルで再現可能な解析を、GitHub Actionsにも気軽に組み込む。
- 事実・不明な範囲を出し、良し悪しと修正判断は後続の人間・AIに任せる。
- 単なる数字の一覧に終わらず、ベストプラクティスに照らして気になる構造が伝わるようにしたい。ただし特定のアーキテクチャを正解にしない。
- 最初は対象アプリのビルド不要。将来的に精密な解析を別モードで追加してもよい。
- GitHubリポジトリはユーザーが使用感を確認してから用意する。ローカルGitで管理する。

## 出発点の実例

1. モデルにメソッド、enumにcaseを追加するだけで実装が積み上がる。
2. os_log / Crashlyticsを包むLoggerがあるのにAnalytics専用ユーティリティが別に作られ、既存の窓口との役割分担を検討したかった。
3. SwiftUI画面に表示要素・状態・分岐を継ぎ足し続ける。

Loggerへの統合が必ず正しいわけではない。統合・分離の選択が無自覚になされることを見逃さない、という問題意識。

## 観測と「見直す理由」を分離する将来の出力案

```text
事実: HomeView.bodyに状態プロパティ2つと条件分岐3つが追加された。
確認の観点: 独立した表示・状態を持つ部分が増えたなら、Viewの分割境界を検討できる。
不明: 状態の所有者やライフサイクルが正しいかは未判定。
```

確認の観点はルールに紐づく固定文にすればLLM不要。ただし事実と混ぜず、根拠の弱い指摘はデフォルト無効も検討する。数を減らすためだけの細切れ分割を促さない。将来 `rationale` / `reviewQuestion` としてJSONにも持たせる案。

## 候補（未実装・採用未確定）

| 候補 | 観測したい事実 | 見直しにつながる理由と限界 |
| --- | --- | --- |
| 依存方向 | 設定された境界を越えるimport/型参照が追加 | Domain→UIなど。役割と許可方向はユーザーが設定し、名前だけで推測しない |
| 依存集中 | 一つの型の参照先が増える | 責務が集中する兆候。ただしcomposition root等は自然に集中する |
| 複数層のバケツリレー | 値・依存が未使用のまま何段も転送 | 中間層の知識を減らせる可能性。DIや境界の維持として必要な転送もある |
| 純粋計算の切り出し候補 | 入力と局所計算だけに依存する領域 | テストしやすい計算へ切り出せる可能性。呼び出し先・getter・時刻・乱数が不明なら純粋と保証しない |
| 副作用の種類の集中 | 永続化・通信・状態更新・イベント送信の追加 | 計算と作用の分離を考える材料。調整役の関数に集約するのは妥当な場合もある |
| SwiftUIの状態・表示の積み上げ | 状態・分岐・クロージャの増加と局所的なまとまり | 所有権とView境界を見直す材料。状態数・bodyの長さだけで悪いとはしない |
| Swift 6の隔離指定の変化 | @MainActor / nonisolated / actor等の追加・削除 | 並行実行の境界に注目できる。言語モード・既定の隔離・toolchain差があり、構文だけで実行executorは断定しない |
| 並行処理の監査ポイント | @unchecked Sendable等の追加 | コンパイラ外で保証すべき前提が増えたことを示す。コンパイラ診断を再実装しない |
| enum対応の分散 | 同じenumに対応するswitch変更の広がり | 分岐の一元化や適切な配置を考える材料。同じcase名だけで同一enumと決めつけない |
| 似た実装の新設 | 新規コードと既存コードの構文類似 | 既存の仕組みの再利用候補。意味上の責務の一致は保証しない |
| APIの拡大 | publicメンバー・protocol要求の追加 | 利用側の知識や実装責務が増える。extension既定実装・アクセスレベルの解決が必要 |
| 循環の新設 | 解決できた参照グラフに新しい循環 | 境界の結びつきが増えたことを示す。曖昧な型名をつないで循環を捏造しない |

初版でも型ヘッダー・メソッド宣言の記述変更として `@MainActor` 等の増減は表示できる。ただし隔離専用の観測・確認の観点・伝播の解析はまだない。

## 初版の次に決めたいこと

2026-09-06追記: PR #81での試用を受け、0.2で「観測のない変更ファイル」「本体比較省略の理由と位置」「token列は変わったが構造指標は同じ本体」を表示。textを型ごとに整理し、引数追加・削除を要約した。JSONはcompactをデフォルトにし、fullを選択可能にした。これは正しさ判定の強化ではなく、観測内容と限界を具体的に示す変更。次は同じPRで使い勝手と読み落とし防止への寄与を再評価する。

1. 実プロジェクトで出力を読み、「普通のdiffより気づきやすい」観測を選ぶ。
2. 多すぎる観測を絞る基準。初版は数値の良し悪しを勝手に決めない。
3. ルール別の有効/無効、抑制と理由、通知優先度、設定ファイルをどこまで必要とするか。
4. 初版の明示型式の比較を改善するか、SwiftUI/引数転送の検出を先に育てるか。
5. 配布方法・OSSライセンス・GitHub Actions workflow。

## 初版で避けたこと

- 型名を見ただけで同じシンボルだと断定するグラフ。
- 品質点数、設計の自動修正、毎回のAI総評。
- 「新しいクラス＝既存クラスに統合すべき」「引数転送＝不要」というルール。
- 意味解析がないのに「副作用なし」「依存循環なし」と言い切ること。
