# Sekkaの目的と未採用の候補

**変更を受け入れる前に、既存の構造へどう組み込むかを見直す入口を作る。** 現在の計画は[ROADMAP](../ROADMAP.md)、判断理由は[0021](decisions/0021-whole-project.md)を参照。

## 目的と対象

コードの変更は局所的でも、状態の所有、役割分担、依存や窓口の配置へ影響する。人間やAIがその関係を考え直せるよう、Swift 6以降の構文上の変化を再現可能に整理する。毎回LLMを動かさず、対象アプリをビルドせずに使える範囲から始める。

Sekka開発自体では、コードだけでなく文書・Issue・マイルストーンが目的に沿うかも見直す。これは開発側の責任であり、現行Sekkaがプロジェクト全体の意味や方針を判定できるという主張ではない。

## 出発点の具体例

- LoggerがあるところへAnalytics専用の窓口を追加する。統合・分離の選択が既存の役割分担と整合しているかを考えたい。
- SwiftUIへ状態・表示・分岐が積み上がる。所有者や分割境界を考える入口が欲しい。
- モデルへメソッド、enumへcaseが増える。自然な拡張か、別の責務も取り込んでいるかを考えたい。

統合や分割が常に正解とはしない。新しいクラス、行数、参照数の増加だけで悪い設計と判定しない。意味上の責務や依存解決が必要なところは、不明な文脈として明示する。

## 観測と出力先

CLIのtext、AIが読むJSON、ローカルで見る図、PRコメントは同じ観測データの利用先として扱う。GitHubで見えることを製品の前提にしない。Mermaidはテキスト出力として両立できる候補で、[Logger例の表示案](validation/diagram-prototype.md)を用意した。解決済みの依存グラフとは区別し、生成機能の採用はまだ決めていない。

## 次に検証する仮説

**新しい処理の組合せが複数の呼び出し側へ広がった事実と、既存の窓口の実装を並べると、局所修正を続ける前に配置を見直す理由へ気づけるか。** #52で送信組合せの拡大・窓口内部の追加・独立した同意セッション・自然な計算追加を対照にした。#54では完全一致する隣接呼び出しの配置だけを機械抽出する実験を行ったが、実PRでの利益は未確認で本番には未採用。次は利用者の実際の困りごとを起こした変更を基準にする。単なる変更一覧や一般的な「分割も検討」では成功としない。

#29はコードと問いの対応付け、#8/#50は主に索引の比較だった。結果は保持するが、本来の目的の有効性を検証済みとはしない。役割設定を先に要求する0030は撤回し、[0031](decisions/0031-structural-success.md)で成功条件を据え直した。設定なしで観測できる関係を先に試し、運用方針が必要な部分を不明として残す。

## 候補（未実装・採用未確定）

| 候補 | 観測したい事実 | 見直しにつながる理由と限界 |
| --- | --- | --- |
| 依存方向 | 設定された境界を越えるimport/型参照が追加 | Domain→UIなど。役割と許可方向はユーザーが設定し、名前だけで推測しない |
| 依存集中 | 一つの型の参照先が増える | 責務が集中する兆候。ただしcomposition root等は自然に集中する |
| 複数層のバケツリレー | 値・依存が未使用のまま何段も転送 | 中間層の知識を減らせる可能性。DIや境界の維持として必要な転送もある |
| 純粋計算の切り出し候補 | 入力と局所計算だけに依存する領域 | テストしやすい計算へ切り出せる可能性。呼び出し先・getter・時刻・乱数が不明なら純粋と保証しない |
| 副作用の種類の集中 | 永続化・通信・状態更新・イベント送信の追加 | 計算と作用の分離を考える材料。調整役の関数に集約するのは妥当な場合もある |
| SwiftUIの状態・表示の積み上げ | 状態・分岐・クロージャの増加と局所的なまとまり | 所有権とView境界を見直す材料。状態数・bodyの長さだけで悪いとはしない |
| Swift 6の隔離指定の変化 | @MainActor / nonisolated / actor等の追加・削除 | 並行実行の境界に注目できる。言語モード・既定の隔離・toolchain差があり、構文だけで実行executorは断定しない |
| 並行処理の監査ポイント | @unchecked Sendable等の追加 | コンパイラ外で保証すべき前提が増えたことを示す。コンパイラ診断を再実装しない |
| enum対応の分散 | 同じenumに対応するswitch変更の広がり | 分岐の一元化や適切な配置を考える材料。同じcase名だけで同一enumと決めつけない |
| 似た実装の新設 | 新規コードと既存コードの構文類似 | 既存の仕組みの再利用候補。意味上の責務の一致は保証しない |
| APIの拡大 | publicメンバー・protocol要求の追加 | 利用側の知識や実装責務が増える。extension既定実装・アクセスレベルの解決が必要 |
| 循環の新設 | 解決できた参照グラフに新しい循環 | 境界の結びつきが増えたことを示す。曖昧な型名をつないで循環を捏造しない |

初版でも型ヘッダー・メソッド宣言の記述変更として `@MainActor` 等の増減は表示できる。ただし隔離専用の観測・確認の観点・伝播の解析はまだない。

## 採用の条件

候補の一覧は実装待ち行列ではない。どの利用場面の検討を助けるか、既存情報の再編集で足りるか、誤誘導と読む負担がどう変わるかを示してから一つ選ぶ。名称・MITでの公開・自身のCI運用は完了済みであり、これらを将来の未決事項として扱わない。
